# E1 · Ola 3/4 · BA-038 · Tope de gasto diario de IA (base de datos)

**Fecha:** 2026-10-18 · **Autor:** Base de datos BuscoEdu (bot), por plan del Orquestador · **Spec:** `buscoedu-knowledge/briefs/e1-ia-multiproveedor.md`, criterios D1–D8
**Base:** `20261018130000_ba034_registros_costo_ia.sql` (Backend) · **Rama:** `feat/e1-integra`
**Estado:** solo local. **No se ha aplicado en prod.** Sin push.

## Qué y para qué
Evitar facturas sorpresa por errores, bucles o abuso. Cada número tiene un tope diario en USD y un umbral de alerta en %, que se editan desde el panel sin redeploy. Al llegar al 100 %, la IA no se llama ese día; a las 00:00 de Bogotá el contador vuelve a cero solo.

| Objeto | Qué hace | Criterio |
|---|---|---|
| `topes_gasto_ia` | Tope (`numeric`, NOT NULL, CHECK > 0) y umbral (1–99) por canal/número. Por defecto USD 5 / 80 %. **No existe la opción sin límite** | D1–D4 |
| Fila inicial + trigger `trg_canales_ia_tope_por_defecto` | Los canales que ya existen y todo canal nuevo arrancan con 5 / 80 | D2 |
| `bitacora_topes_gasto_ia` | Guarda campo, valor anterior → nuevo, actor y fecha. Solo registra cambios reales | D1 |
| `precios_modelo_ia` | Precio USD por 1.000 tokens por proveedor + modelo, con su versión y fuente. Nunca se sobrescribe: se cierra la versión vigente (`vigente_hasta`) y se inserta la nueva (`reemplaza_precio_id`). Hay una sola versión vigente por modelo | Pedido de Backend en BA-034 |
| `alertas_gasto_ia` | Una alerta por canal, día de Bogotá y tipo (`umbral` / `corte`); `vista_en` sirve para marcarla como vista | D5, D6 |
| Índice `idx_registros_costo_ia_canal_creado` | Hace rápida la suma del gasto de hoy por canal | D6 |
| `fn_ia_actualizar_tope(canal, tope, umbral, actor)` | Valida y devuelve el motivo en español: «El tope es obligatorio y mayor que 0» y «El umbral de alerta debe estar entre 1 y 99 %». NULL = no cambiar ese campo. Escribe la bitácora | D1, D3, D4 |
| `fn_ia_gasto_hoy(canal)` | Devuelve `{gasto_usd, tope_diario_usd, umbral_alerta_pct, pct_usado, estado: normal\|alerta\|cortado, dia_bogota, intentos_sin_costo}`. Si el canal no tiene fila, usa 5 / 80 | D5–D8 |
| `fn_ia_registrar_alerta_gasto(canal)` | Registra la alerta del día sin duplicarla. Si se pasa de golpe al corte, deja también la alerta de umbral | D5, D6 |
| `fn_ia_registrar_precio(...)` / `fn_ia_precio_vigente(proveedor, modelo)` | Crean una versión nueva de precio y leen la vigente con la misma forma que `PreciosModelo` | — |

**Permisos:**
- Las tablas tienen RLS: solo super_admin puede leerlas, y anon y authenticated no pueden escribir.
- Las funciones solo las puede ejecutar `service_role`. El endpoint verifica que quien llama sea super_admin y pasa el actor.

## Decisiones y supuestos (⚠ revisar)
1. **«Número» = canal hoy.** Todavía no existe `lineas_whatsapp` (Centro WA), y `registros_costo_ia` guarda `canal_codigo`, no la línea. Como hoy hay un solo número de WhatsApp, el tope se guarda por canal (`web`, `whatsapp`, …). Cuando exista `lineas_whatsapp`, hay que agregar `linea_id` a `topes_gasto_ia`, `alertas_gasto_ia` y `registros_costo_ia`, y cambiar la restricción de unicidad.
2. **Las simulaciones cuentan para el gasto** (`modo_simulacion = true` también cuesta dinero si llama al proveedor).
3. **Gasto parcial:** los intentos sin costo conocido (por ejemplo, Abacus sin precio cargado) no suman al gasto, pero se cuentan en `intentos_sin_costo` para que el panel avise. No se inventa ningún precio.
4. **D7 sin tareas programadas:** el «día» se calcula en cada consulta con `America/Bogota`. Al subir el tope, el siguiente `fn_ia_gasto_hoy` ya responde `normal`.
5. `parametros_globales` no existe en la BD. Los valores por defecto (5 / 80) quedan como DEFAULT de la columna y en la función.

## Contrato para Backend (BA-038)
- **Antes de cada llamada a la IA:** `rpc('fn_ia_gasto_hoy', {p_canal_codigo})`.
  - Si `estado = 'cortado'`: no llamar a la IA, enviar el mensaje de C3 y luego `rpc('fn_ia_registrar_alerta_gasto')`.
  - Si `estado = 'alerta'`: `rpc('fn_ia_registrar_alerta_gasto')` y seguir.
  - Si la RPC falla: aplicar fail-closed según la regla que decida Backend o el Orquestador.
- **Panel:** guardar con `rpc('fn_ia_actualizar_tope')`, mostrar `motivo` cuando `ok = false` y leer el estado con `fn_ia_gasto_hoy` (D8).
- **Precios:** `fn_ia_precio_vigente(proveedor_codigo, modelo)` puede reemplazar `configuracion_tecnica.costo_usd_1k_*`. Si devuelve NULL, el costo queda en null, igual que hoy.

## Pruebas locales (Postgres 17 + mocks de `canales_ia`, `proveedores_ia`, `usuarios_internos` + migración 130000 real)
- La migración corre 2 veces seguidas sin error ✓
- Los valores por defecto 5 / 80 quedan en web y whatsapp, y también en un canal nuevo creado por el trigger ✓
- Rechazos con su motivo:
  - Tope 0 → `tope_invalido` ✓
  - Tope negativo → `tope_invalido` ✓
  - Umbral 0 → `umbral_invalido` ✓
  - Umbral 100 → `umbral_invalido` ✓
  - Sin valores → `sin_cambios` ✓
  - Canal inexistente → `canal_inexistente` ✓
- Un `UPDATE` directo en la tabla con NULL o con umbral 100 lo rechazan las restricciones de la tabla ✓
- Con un gasto de 4,10 sobre 5, el estado es `alerta` (82 %) e `intentos_sin_costo` = 1 ✓. La fila de 50 USD de 1 segundo antes de la medianoche de Bogotá no se cuenta ✓
- 9 sobre 5 → `cortado` y se guardan las alertas `umbral` y `corte`. Al repetir la llamada no se duplican ✓
- Al subir el tope a 20, el estado pasa a `normal` ✓. La bitácora guarda 5→20 y 80→90; guardar el mismo valor no agrega fila ✓
- Precios:
  - Sin precio → NULL ✓
  - Versión repetida → `version_existente` ✓
  - Precio negativo → `precio_invalido` ✓
  - Versión nueva → cierra la anterior; quedan 2 versiones y 1 vigente ✓
- anon y authenticated → `permission denied`; service_role → OK ✓
- Deshacer → las 4 tablas quedan como `_retirada_20261018` y se quitan las funciones ✓. Reaplicar después funciona y crea los índices completos ✓
