## BA-035 · Claves de IA en Supabase Vault
**Migración:** `supabase/migrations/20261018110000_ba035_vault_claves_ia.sql` · **Deshacer:** `supabase/ops/20261018_ba035_deshacer.sql`

| Objeto | Qué hace |
|---|---|
| `proveedores_ia` + `origen_secreto` (`env`/`vault`, por defecto `env`), `referencia_secreto`, `clave_actualizada_en`, `clave_revocada_en` | Guardan solo metadatos, nunca el valor. Los proveedores actuales (Abacus) siguen en `env` sin cambios |
| `bitacora_claves_ia` | Registra quién guardó, reemplazó o revocó una clave y cuándo (A4), sin el valor. RLS: solo super_admin puede leerla, y solo escribe la función |
| `fn_ia_guardar_clave(codigo, clave, actor)` | Crea o reemplaza el secreto `ia_proveedor_<codigo>` en Vault. Devuelve `{ok, accion, referencia}` y **nunca** la clave |
| `fn_ia_revocar_clave(codigo, actor)` | Sobrescribe el valor con uno aleatorio (la clave real deja de existir) y marca `clave_revocada_en`. Sin DELETE físico |
| `fn_ia_leer_clave(codigo)` | Devuelve la clave en claro **solo al servidor**. Da NULL si el proveedor no usa Vault, si no hay secreto o si la clave está revocada |
| `fn_ia_estado_clave(codigo)` | Devuelve el estado para la pantalla («Configurada ✓ / Falta ✗», origen y fechas), sin el valor |

**Permisos:** las 4 funciones tienen `REVOKE` para PUBLIC, anon y authenticated, y `GRANT` solo para `service_role`. El endpoint de Backend verifica que quien llama sea super_admin y llama por RPC.

**Reglas para Backend (BA-036):**
- Llamar siempre por RPC con parámetros; nunca armar el SQL con la clave adentro.
- No registrar en logs el body del POST de la clave.
- Usar `fn_ia_leer_clave` solo en memoria y en el servidor.
- Los errores devuelven solo el código y el `sqlstate`, nunca `SQLERRM`, para que la clave no aparezca en mensajes.

**Pendiente al aplicar en prod (con OK de Jhon):**
- Revisar con una consulta de solo lectura las firmas de `vault.create_secret` y `vault.update_secret` en `supabase_vault` 0.3.1. La migración las llama con argumentos posicionales: (secreto, nombre, descripción) y (id, secreto).
- Confirmar que los logs de Postgres no registran los parámetros de las RPC.

## Pruebas locales (Postgres 17 con Vault simulado: mismas tablas, vistas y funciones `create_secret`/`update_secret`)
- Las dos migraciones corren 2 veces seguidas sin error (idempotentes) ✓
- `fn_cambiar_etapa`:
  - Subestado NULL → `subestado_requerido` ✓
  - Subestado de otra etapa → `subestado_invalido_para_etapa` ✓
  - Subestado válido → ok, con 1 fila en el historial ✓
- Vault:
  - Al guardar, la acción es `guardar` y la clave se lee bien ✓
  - Al volver a guardar, la acción es `reemplazar`; se lee la clave nueva, con los espacios recortados ✓
  - Al revocar, la lectura da NULL y en Vault queda 0 claves reales ✓
- La bitácora registra `guardar,reemplazar,revocar` y en ninguna fila aparece la clave ✓
- Clave corta → `clave_invalida` ✓ · proveedor que no existe → `proveedor_inexistente` ✓
- anon y authenticated → `permission denied` en guardar y en leer ✓ · `service_role` → OK ✓
- Estado de Abacus (`env`, con nombre de variable en `despliegues_ia`) → configurada ✓
- Los dos scripts de deshacer corren limpio: quitan las funciones, renombran la bitácora (no la borran), quitan las columnas y `fn_cambiar_etapa` vuelve a la versión 150200 ✓
