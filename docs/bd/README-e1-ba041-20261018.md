**Autor:** Base de datos BuscoEdu (bot) · **Fecha:** 2026-10-18 · **Rama:** `feat/e1-integra` (solo local, sin push, sin prod)
**Pedido:** Orquestador, E1 · Ola 4/4 · BA-041. Spec: `briefs/e1-ia-multiproveedor.md` §G.

## Journey
Cuando un estudiante aplica a una beca, la conversión crea la persona, sus consentimientos, la oportunidad (lead) y la propuesta. Antes, la función **escribía primero y revisaba después**, y nunca revisaba ni que la oferta siguiera vigente ni que el estudiante hubiera autorizado contacto. Podían quedar leads sin consentimiento, leads sobre ofertas vencidas o filas a medias. Ahora todo se valida al principio: si algo falla, **no se escribe nada** y se devuelve el motivo.

## Validaciones (en orden, antes de cualquier INSERT/UPDATE)
| # | Regla | Error si falla |
|---|---|---|
| — | Clave de idempotencia, oferta y celular (ya existía) | `clave_idempotencia_requerida`, `oferta_id_requerida`, `celular_requerido`, `oferta_inexistente` |
| — | Misma clave ya convertida → devuelve la existente (ya existía) | `ok:true, idempotente:true` |
| V1 | Oferta `activo` + `estado_publicacion = 'publicado'` + `estado_validacion = 'validado'` | `oferta_no_disponible` |
| V1 | Vigente hoy, en hora de Bogotá: `vigente_desde ≤ hoy` | `oferta_no_vigente` |
| V1 | `vigente_hasta` nulo o `≥ hoy` | `oferta_vencida` |
| V2 | La oferta tiene periodo académico | `oferta_sin_periodo` |
| V3 | Todos los consentimientos obligatorios activos con `otorgado = true` (booleano JSON; el texto "true" no cuenta) | `consentimiento_obligatorio_faltante` |
| V3 | Al menos una autorización de contacto (`contacto`, `contacto_comercial`, `whatsapp`, `contacto_whatsapp` o `transferencia_universidad`) | `consentimiento_no_aceptado` |
| V4 | El embudo tiene etapa inicial (antes se revisaba después de crear la persona) | `etapa_inicial_inexistente` |
| V5 | Si la persona ya existe: `fn_validar_aplicacion` (duplicado activo y máximo 3) | `duplicada`, `limite_alcanzado` |

Todo lo demás queda **igual**: persona, consentimientos, oportunidad, historial, asignación, aplicación, propuesta, y transferencia solo `por_lead` con consentimiento de transferencia (sin él, sigue la nota «pendiente de consentimiento»). La excepción ya no devuelve `detalle` (SQLERRM), solo `sqlstate`.

**Permisos (hallazgo):** en el repo nunca se revocó EXECUTE, así que `anon` y `authenticated` podían llamar esta función por RPC y crear leads sin pasar por la API. Ahora EXECUTE es solo `service_role`, que es lo que usa `app/api/leadcenter/convertir`. BA-031 la llama desde otra función SECURITY DEFINER y no se afecta.

## Impacto en Backend / Frontend
- Hay códigos de error nuevos que la API debería traducir a español para el usuario: `oferta_no_disponible`, `oferta_no_vigente`, `oferta_vencida`, `oferta_sin_periodo`, `consentimiento_obligatorio_faltante` y `consentimiento_no_aceptado`.
- Ya no llega `detalle` en el error `excepcion`.
- La regla de oferta es la misma que usa NaIA (`app/api/naia/route.ts`), con una diferencia: NaIA calcula «hoy» en UTC y aquí se usa la hora de Bogotá.
